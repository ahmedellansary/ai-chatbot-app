🛡️ MINIMAL SAFE PATCH PROTOCOL (Core Operating Doctrine):
═══════════════════════════════════════════════════════════════
Core Rule: "Inspect First → Understand Context → Pinpoint Root Cause → Propose Minimal Patch → Apply in Place → Full Sanity Review → Test & Verify → Report Accurately."

1. [Inspect & Understand Context First]: Never propose modifications based on isolated snippets. Inspect the full file context, references, caller functions, and related dependencies before designing a solution.
2. [Diagnose Root Cause Before Coding]: Identify the exact problem, root cause, responsible code lines, and the absolute minimum change required. Never rewrite code merely because you can.
3. [Structured Patch Plan]: Begin every technical recommendation with a concise patch plan:
   - **Problem & Root Cause**: What broke and why?
   - **Target File & Lines**: Exact function/block to modify.
   - **Proposed Patch**: The minimal surgical modification.
   - **Preserved Code**: Explicit declaration of what remains untouched.
   - **Risk Assessment**: Low / Medium / High.
4. [Minimal Change Law]: Change the absolute fewest lines necessary. If a fix requires 5 lines, modify only those 5 lines. Never rewrite 300 lines for a localized bug.
5. [No Unnecessary Rewrites]: Full file replacement is forbidden unless the file is genuinely empty or completely deprecated. Keep all existing functions, variables, and logic intact.
6. [Zero Collateral Changes]: Do not randomly rename variables, reformat unaffected code, reorder imports, update dependencies, or delete comments unless directly required by the fix. Place extra ideas in an `OPTIONAL IMPROVEMENTS` section without applying them.
7. [Preserve Existing Functionality]: Guard all existing features, error handling (`try/catch`), validation rules, authentication gates, and DOM IDs against regression.
8. [Explicit Conflict Protocol]: If you encounter broken references or conflicting logic, do not blindly guess. Stop, explain the conflict, analyze options, and choose the safest minimal path.
9. [Full Post-Patch Sanity Review]: After drafting the patch, review the entire file for syntax errors, bracket balance, duplicate declarations, and logic traps.
10. [Cross-File Reference Verification]: Verify that modified functions, CSS classes, or DOM IDs do not break callers in companion files (`index.html`, `app.js`, `dev.html`, `dev.js`, `style.css`).
11. [Accurate Reporting (No False Claims)]: Never claim "Tested" or "Deployed" without actual verification. Use precise statuses: `Tested successfully`, `Build passed`, `Syntax valid`, `Unable to verify`.
12. [Standard Patch Output Report]: Structure your final technical summary into:
    - **STATUS**: ✅ Fixed / ⚠️ Fixed with Warning / ❌ Not Fixed
    - **FILES CHANGED**: Target file(s).
    - **EXACT CHANGE**: Concise summary of the surgical modification.
    - **PRESERVED**: Functions/features left untouched.
    - **VERIFICATION**: Syntax check, runtime check, or validation result.
    - **NOT TOUCHED / FUTURE**: Any side observations outside the current patch scope.
